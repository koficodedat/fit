## 2. Roadmap / phasing document

**Found.** `docs/FIT-SYNTAX.md` §11 ("What is out of scope for v0.1"), split into §11.1 ("Hard out-of-scope — not planned, ever") and §11.2 ("Deferred to a later version — not in v0.1 but consistent with FIT's direction"). This is the closest thing to a roadmap in the repository — no separate "v0.2 plan" or numbered-phase document exists anywhere else. `FIT-SPEC-v2.md` §11 ("Execution path") is a three-line phase sketch (Design → Build → Decision) but does not enumerate features.

**1. What it says about expression syntax, literals, or arithmetic: nothing, anywhere.** Neither §11.1 nor §11.2 mentions literals, numeric expressions, or arithmetic in any form. Searching the entire document for "literal" (any case) returns zero matches. The document has no expression-grammar section at all — its table of contents runs `§1 Notation` → `§2 Type declarations` → `§3 Function signatures` → `§4 Bindings and mutation` → `§5 Control flow` → ... — control flow, but never a standalone treatment of what can appear in an expression position. §1.1 ("Lexical") defines identifiers, keywords, and comments as token categories; it defines no literal token of any kind.

Cross-checked against actual usage: no `.fit` file anywhere in the repository — not one of 372 tests' fixtures, not either canonical program, not `examples/postgres/postgres.fit` — contains a string literal, a boolean literal, or (per the prior investigation round, `189fa4d`) a working integer literal. Every value in every FIT program in this repository is obtained from an extern call. This is a broader and more precise fact than "no integer literals": **there is no literal syntax of any kind, and the roadmap document is silent on the omission rather than declaring it deliberate.**

So, directly answering what this round exists to settle: **"no integer literals" is not documented as deliberate anywhere.** It is also not documented as a gap, an oversight, or planned. The roadmap document simply never addresses the question, in either direction. Whether the omission is in fact intentional (consistent with "every canonical program obtains values from externs," which is true of the whole corpus, not just the canonical programs) is a reading that the code's behavior supports and the roadmap neither confirms nor denies.

**2. What phase v0.1 is scoped to deliver:** §11's split is normative for the whole project — §11.1 is permanent ("not planned, ever" — fails FIT's §12 functional-discipline filter), §11.2 is "not in v0.1 but consistent with FIT's direction" (deferred, not rejected). No separate document states what v0.1 *positively* commits to deliver as a checklist; that has to be read as the complement of §11's exclusion lists plus whatever `FIT-SYNTAX.md` §§1–10 describe as present.

**3. Does actual v0.1 work match what was planned?** Partially, with three specific items in §11.2 now stale (built despite being listed as not-yet-built) — detailed in §3 below. Modules, which the originating brief for this round suspected were still listed as excluded, are **not** stale in the current live file — §9 fully specifies the module system that shipped in `7552273`/later module-system work, matching the implementation. (The brief's own context section describes this as a discrepancy found against a copy in "project knowledge," which this audit cannot check — see §1's `FIT-SPEC.md` note above for the same caveat.) What *is* stale, found independently in this round: match exhaustiveness enforcement and mutual-recursion lend/move inference, both listed in §11.2 as deferred, both actually shipped.

| §5.2 loops | Says anything about ownership across iterations? | **Partially diverges, precisely.** Direct quote: "Linear values introduced inside the loop body must be consumed before `break`." ## 5. Cross-document contradictions

Two authoritative documents disagreeing, both claiming currency:

1. **`FIT-SYNTAX.md` §5.3 vs. `poc-findings.md` "Rule count: 8 → 9" / `FIT-SPEC-v2.md`'s implicit rule-10 count, on match exhaustiveness.** `FIT-SYNTAX.md` states exhaustiveness is deferred to v0.2 and unenforced; `poc-findings.md` documents it as shipped, rule 9, with implementation commit `731ba2c` and its own probe round. The two documents describe the current behavior of the same feature oppositely.
2. **`FIT-SYNTAX.md` §2.1 vs. `FIT-SPEC-v2.md` §2.3, on record fields.** `FIT-SPEC-v2.md` §2.3 states plainly: "its fields must therefore be **unrestricted**... A record field of linear type... is a compile error." `FIT-SYNTAX.md` §2.1 still reads as though a record may hold a resource field (just remain non-linear itself). Both are labeled authoritative; they disagree on whether the same program is legal.
3. **`FIT-SYNTAX.md` §11.2 vs. `src/types.ts` + `poc-findings.md`, on mutual-recursion inference** — same pattern as #1, different feature.
4. **Three-way numeric contradiction, none matching current reality:** `README.md` states "251 tests" and "802 total lines" (parser 501 + checker 301); `CLAUDE.md`'s embedded PoC-status section states "299 tests across 7 suites" and "total: 1479" lines; the actual current repository (this session, verified by running the suite and `wc -l`) is **372 tests across 10 suites**, and **2560 total lines** across `src/*.ts` (ast 60, parser 598, checker 594, types 407, loader 82, main 45, codegen 774). All three numbers disagree with each other and with the present state; none is labeled as a historical snapshot. `poc-findings.md`'s own most recent phase-section total (2383, as of the codegen-completion phase, itself now two rounds stale) is closer but still not current, and — unlike its sibling phase sections — the document's *top-level* Q1 line-count table (1479) is presented without the "point-in-time, not refreshed" convention that the document states applies to phase sections specifically (line 184), leaving a reader no signal that the top table is equally frozen.

No contradiction found that would make a *currently passing test* wrong (escalation trigger 1 did not fire — every divergence found is documentation trailing the implementation, not documentation the implementation itself contradicts in a way a test would catch).
